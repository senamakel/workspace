# Local Workflow Preferences

- Default to executing, not planning. When a task is clear and well-scoped, make the change directly — do not open a separate plan or design phase, and do not stop to ask for approval before starting. Reserve an explicit plan or design doc for work that is genuinely large, ambiguous, risky, or when the user explicitly asks for one.

- Don't stop to ask when the next step is obvious and the request already authorizes it. Pick the sensible default, proceed through the whole task, and report what you did at the end. Ask only when you are truly blocked on a decision that is the user's to make — an irreversible or destructive action, or a real fork with no clear default.

- For any new implementation or audit work, run `worktree <slug>` before editing and work inside the reported `./worktrees/<slug>` path. The command creates or reuses the matching feature branch and initializes recursive submodules. Do not do new work directly on `main`.

- For cross-repo changes in a workflow checkout (a superproject with submodules), create the worktree at the **superproject** level only: run `worktree <slug>` from the workflow folder. Inside each submodule you touch, use a feature branch in place — `git -C <submodule> switch -c <slug>` — because submodules are checked out detached at the recorded gitlink; branch before editing. Never create a nested worktree inside a submodule. Commit and PR each submodule branch to that submodule's own upstream, then commit the updated gitlinks on the superproject branch.

- Always raise PRs against the **upstream** canonical repo (e.g. `tinyhumansai/*`), never a personal fork. `origin` may point at a fork (e.g. `senamakel/*`); when it does, push the branch and open the PR against the `upstream` remote. If the PR's base branch only exists locally/on the fork, push it to upstream first so the PR can target it there.

- Open PRs ready for review, not as drafts. `gh pr create` without `--draft` is the default. A draft is invisible to my own tooling — `pr-list` excludes drafts, `pr-merge` refuses them, `pr-fix` skips them without `PR_FIX_ALLOW_DRAFT=1`, and `repo-orchestrate` never triages one — so a needlessly drafted PR silently drops out of every automated sweep. Use `--draft` only when the PR genuinely must not merge yet — work still in progress, a dependency PR that has to land first, or a deliberate request for early feedback on an incomplete change — and say in the body what has to happen before it is ready. When a draft becomes complete, mark it ready with `gh pr ready <number>` rather than leaving it parked.

- Work PR review feedback with the `pr-comments` / `pr-reply` / `pr-review-resolve` trio rather than raw `gh api` calls. `pr-comments [<number>] [--json]` lists every unresolved thread plus the review bodies and top-level comments, so `coderabbitai`, `chatgpt-codex-connector`, and `greptile-apps` are all covered — GitHub splits bot feedback across three channels and reading only inline threads silently drops most of it. Answer each thread with `pr-reply <threadId> --body "<reply>"`, which replies and resolves in one step; pass `--no-resolve` when the reply asks the reviewer a question instead of closing the point. Leave a real reply on every thread you resolve — silently resolving a comment hides an unaddressed objection. Never resolve a thread whose feedback you have not actually addressed or explicitly declined with a reason.

- Clear a changes-requested verdict by fixing it, not by dismissing it. `pr-review-resolve --list` shows which reviews still block; after pushing the fix use `--re-request` so the reviewer re-reviews. `--dismiss <reviewId>` and `--dismiss-all` are the last resort, require a `--message` saying why, and must never be used to retire feedback that is still valid. Approving is a reviewer's action on someone else's PR (`--approve`); GitHub rejects approving your own.

- Committing is automatic: an `auto-commit` PostToolUse hook checkpoints the working tree every few tool calls, so do not commit as you go. Commit by hand only when a specific commit matters — then use `atomic-commit "<scoped message>" -- <files...>`, which is also what the hook calls.
